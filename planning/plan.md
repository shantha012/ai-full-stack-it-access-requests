# Build plan

## Choices

- Runtime: Python 3.10+ with the standard library for CLI, HTTP, hashing, SQLite and unittest, plus a pinned JSON Schema validation dependency and lockfile; this fits the supplied Python starter and keeps setup small.
- Interface: a CLI with proposed `python3 -m access_requests intake`, `queue`, `resume`, `retry`, `history`, `export` and `accuracy` subcommands; separate processes can inspect completed records while workers continue intake.
- Test command: `env -u API_KEY python3 -m unittest discover -s tests`; all planned tests inject saved replies, errors, clocks and HTTP transport, with real network access blocked, so no step or test requires API_KEY.
- Provider call: default mock adapter plus an implemented OpenAI Chat Completions HTTP adapter using an injected `urllib.request` transport; configure endpoint/model and request settings, load API_KEY only for optional live use, send the extraction schema and policy-bounded prompt, and validate response completion/refusal before JSON parsing and schema/semantic checks.

These are proposed implementation choices, not added requirements. This file is a plan only: no application, fixtures or tests have been created, and no application behavior or accuracy has been measured. Proposed case IDs below replace the illustrative test names in the spec without changing its requirements. The spec remains unchanged.

Provider contract research: the [Chat API reference](https://developers.openai.com/api/reference/resources/chat) and [structured output guide](https://developers.openai.com/api/docs/guides/structured-outputs) describe completion finish reasons and refusal handling. The adapter will treat refusal and non-success completion as explicit errors, including syntactically valid but incomplete content; local schema validation remains required. These documents inform the adapter choice, not business requirements. Exact live model access is not presumed; record the configured model in evidence and document the supported wire contract, with live observations optional and separately labelled.

Proposed operational design: one SQLite database on a single host/local disk shared by regional operators through the same CLI host; do not claim multi-host/network-filesystem support. Keep immutable source-byte revisions and attempt records, current pointers and pending/running/completed states in transactions. Acquire per-document work claims briefly; make provider calls outside transactions; protect publication with attempt/revision checks. Use configurable bounded workers, timeouts and finite rate-limit retries with injected clocks in tests. Completed documents become visible immediately. Resume interrupted claims after safe lease recovery, retaining already completed work. Configuration provenance includes provider, endpoint, model, extraction prompt/schema hashes and relevant request settings; policy content hash identifies routing policy. Changing only routing policy can reroute a preserved valid extraction; changing extraction settings triggers extraction. Credentials do not enter fingerprints, logs or evidence.

Export design: SQLite is authoritative for live `queue` reads; publish immutable export generations containing both deliverables from one database snapshot, then switch one current-generation reference atomically. Document the portable committed copies at `deliverables/extractions.jsonl` and `deliverables/queue.json` as a completed generation; readers performing concurrent inspection use the CLI or generation reference, not two independently opened files during a copy. Keep history outside current JSONL outputs.

Unresolved interpretations from the spec have been raised with the user and stay open: (a) ambiguous/conflicting facts on a withdrawal with present ID/date, and (b) which revision is latest when different contents for the same filename arrive concurrently. No timestamp or completion-order rule is invented here. Build ordinary ordered-batch and identical-revision overlap cases; defer contested-revision publication and contradictory-withdrawal expectations until clarified. Detection of unfamiliar instruction overrides, free-text purpose equivalence and the exact facilitator capture procedure also remain limits to document. No numerical throughput target is inferred from daily/burst volumes.

## Test plan

Each row is a separate future test. Paths without a directory under Input mean `materials/requests/`; derived/new inputs are authored fixtures, not existing supplied files. Successful-response filenames are planned canned provider envelopes, not oracle files. T05–T24 list all 12 scalar facts for all 20 originals; `supporting_quotes` must be exact evidence substrings and `issues` must express the listed missing/conflicting facts without requiring a particular sentence or code. The requested business purpose is represented here by a chosen exact supporting sentence; extra source-supported explanation is not automatically a factual error. Error responses have null extraction, so no scalar business fields are fabricated.

Expected facts are fixed before application execution. Every T05–T24 Source cell quotes its complete decoded message, which supports its identity, dates, requester/team, access fields, manager and purpose; the appended policy quote supplies status/owner/next action and null/conflict/correction rules. Supporting evidence may use shorter exact substrings; a whole-message quote is not mandated. Array exact matching and free-text purpose normalization are accuracy-method choices to document, not additional office policy.

Proposed accuracy rules: score the 11 non-purpose scalar fields per document by exact value including null (21 × 11 = 231 comparisons); separately report business_purpose against the explicitly chosen reference sentence, supporting-quote substring validity and issue semantic coverage. Treat missing keys as failures, exclude no hard cases from the denominator, report per-field/per-document mismatches and disclose that exact wording may differ despite factual equivalence. If purpose exact matches are also reported, give the separate 21-comparison denominator. Human inspection of source-supported alternative purposes remains necessary. These are chosen reporting rules, not a required accuracy threshold. Saved mocks measure pipeline/comparator behavior, not generalization or live model accuracy.
