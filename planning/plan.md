# Implementation plan

## 1. Choices

This document preserves the original implementation plan and records the S16/S17 follow-up work. R-numbers refer to `planning/spec.md`; Q-numbers retain its open questions. S01–S15 retain their original build instructions; their observed results are recorded separately rather than inferred from the plan. S16/T30–T32 document the exact-quote validation change; S17/T33–T36 and C07 cover boundary intake, date syntax, durable failure/retry and report attribution; observed results are linked from `planning/validation.md`, `planning/quote-validation-test-run.txt` and `planning/evidence/acceptance-gaps-review.md`. S16 does not claim an observed initial failure; S17 records its targeted failing date-format run and subsequent repair in `planning/evidence/acceptance-gaps-review.md`.

- **Runtime:** Python 3.10+ with SQLite for durable state and `jsonschema` for the supplied extraction schema; this follows the classroom runtime and supports transactional current/history updates. Use a pinned `uv.lock` and document the tested Python and uv versions during implementation.
- **Interface:** a CLI (`python -m access_requests`) with `intake`, `queue`, `attempts`, `resume`, `retry`, `refresh`, `export` and `accuracy` commands; regional operators can run separate processes against one database on one host.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests`; mock the provider and HTTP transport, prohibit network connections, and use temporary databases/directories. Installation is separate from running tests.
- **Model calls:** use the implemented OpenAI Responses API HTTP adapter behind a provider interface, with provider/model, endpoint, timeout, output budget and worker count configurable; use `API_KEY` only for an explicitly selected real-provider run. The selected contract and its recorded provider review are in `planning/evidence/provider-review.md`: pinned default model `gpt-4.1-mini-2025-04-14`, separate instructions/user input, and `text.format` with `type=json_schema`, `strict=true` and the configured schema. Local validation always uses the repository schema; `--schema-file` changes only the provider request schema. Fake transport checks exercise the implemented adapter using test-created configuration, saved replies and no network; they never require a caller-provided API_KEY.

Engineering choices (not Northstar business rules):

- SQLite transactions contain source revisions, immutable attempts, settings/policy fingerprints, work claims and the pointer to each document's current terminal attempt. Never hold a database write transaction across a model call. Use bounded workers, configurable deadlines and expiring claims; a crash may require repeating a provider call. Do not promise exactly-once calls or multi-host SQLite operation.
- Hash original file bytes, not normalized JSON. Cache terminal results by document ID, byte hash and producing-settings fingerprint. Include provider/model, prompt, schema, request options and policy bytes/version in the fingerprint. Policy changes initially trigger full re-extraction for simplicity. Ordinary reruns reuse terminal failures as well as successes; explicit retry/refresh bypasses reuse and records a new attempt.
- Allocate monotonic document generations at intake registration. Within this implementation, the last registered generation is the desired source; a late response from an earlier generation remains in history and cannot replace it. This is an explicit ordering convention for Q-41, not an order inferred from hashes or timestamps.
- Show pending/running work separately in `attempts`/`queue --pending`; completed records remain inspectable. Once a later attempt completes with an error, it becomes the current error. Any earlier completed result displayed during pending work is labelled with its earlier hash, attempt and settings.
- Keep history in database tables separate from current export files. The CLI reads one database transaction. Build `extractions.jsonl` and `queue.json` from the same transaction into an immutable generation directory; atomically switch a `deliverables` symlink to that generation on supported POSIX local filesystems. Each file carries the generation identity, and documented external readers resolve the symlink once and read both files from that resolved directory. Serialize exporters and reject stale publication. Independent unsynchronized reads across two generations are outside the supported reader contract. Verify packaging preserves the required deliverable paths.
- Queue entries include document ID, attempt ID, source hash, settings/policy version and the routing triple. Current records include the brief's fields plus provenance. Errors contain a category, redacted explanation and exact retry command. Never store credentials in fingerprints, evidence, history or log payloads.
- Start with a flat input directory and unique basenames; preserve absent documents across later batches. Treat other topologies, malformed exports, unsupported input versions and files beyond the stated message range as documented limits until Q-02–Q-05 are resolved. A message of exactly 200 whitespace-separated English words is a positive boundary example, not a new rejection rule.
- Test scale: a deterministic 2,000-document mock batch, bounded concurrency and two overlapping CLI processes on a local database. This checks functional scaling and sharing assumptions; it establishes no live throughput or latency promise.

**Policy questions needing a person before affected assertions are finalized:** Q-21/Q-54: must business_purpose be a verbatim span or may it be a factual summary? Below, quoted purpose spans are independent scoring references, not a claim that equivalent summaries are prohibited. Q-29: IT-006 combines a legitimate read request with injected admin text; routing/evidence are fixed, but the permission scalar remains undecided. These questions have been raised with the user; do not silently select an answer. Q-31/Q-32: incomplete withdrawals and schema-valid but unsupported scalar facts still need an agreed retry-versus-clarify rule before those additional edge cases are implemented. For Q-32, S16 rejects quotes outside the decoded message and S17 rejects malformed non-null date syntax as invalid-response before routing, using the existing extraction-failure path. Calendar-validity and unsupported scalar-fact classifications remain open. Exact matching does not decide evidence completeness or factual relevance. Known cases below use the policy's explicit rules.

The remaining Q-01–Q-65 remain as recorded in the spec. The choices above settle implementation details only within the documented limits; they do not add alias maps, ownership directories, approval/provisioning, date-boundary rules, multi-request splitting or new business requirements. Q-47/Q-48 have an implemented contract recorded in the provider review; Q-49 requires agreement on failed real-attempt response_source (all failure tests here use `mock`). Q-62/Q-64 require facilitator instructions before submission.

### How to read the expected evidence

Business facts come from literal message words plus the quoted office-policy rule. L01–L20 below provide field-by-field pairs, not just a reference to an entire message. A01–A09 have complete authored inputs and an authored-field evidence table below. Every case's Source cell points to those pairs and also quotes its deciding rule. A null is supported by a full-message absence check or quoted unresolved/conflicting wording; an issue follows the quoted null/conflict rule. For supporting_quotes, assert exact substring membership and the explicitly listed conflict/attack evidence, without inventing a required number or ordering of quotes. Purpose spans are independent references; Q-21/Q-29 remain unresolved rather than being treated as accepted facts.

Provider failures, refused/incomplete envelopes, response mutations, file hashes and process states are not message facts. Their rows identify the injected condition, quote the applicable recovery/schema/requirements rule, and label any extra test mechanism as an implementation choice. Filename/hash/provenance facts use the input bytes/configuration and the explicit policy/brief rule; they cannot honestly be supported by a natural-language request quote.
